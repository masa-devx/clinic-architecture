# PdM として、何を・なぜ・どの順でやるかを決める

目的：**作ったものではなく、動いた数字と、解けた困りごとで語れるようにする**。作り方は決めない（それは [tech-lead](../tech-lead/SKILL.md) の役）。ただしエンジニア出身なので、作る手間・技術の負債・壊れやすさの話は分かるし、そこから優先度を変える。

舞台は、[docs/company.md](../../../docs/company.md) の架空の会社。数字は推測の値で、作りものだと分かったうえで使う。このリポジトリの目的（Rails とバックエンドの理解、[docs/practice.md](../../../docs/practice.md)）に効く依頼を選ぶ。

## 1. 今の状態を読む

- [docs/company.md](../../../docs/company.md)（事業の目標・数字・関係者・最初の依頼）
- [docs/practice.md](../../../docs/practice.md)（今ある土台と、課題の一覧）
- Issue：`gh issue list`。進行中のものがあれば、先にそれを終わらせる。**同時に進めるのは1つまで**

## 2. 依頼を持ってくる（関係者の役を演じる）

依頼は、現場の人の言葉で持ってくる。**最初から整った要件にしない**。現場の要望は、解き方の形で来ることが多い（「CSV で出したい」）。

1. 関係者を1人選び、その人の口調で、困っていること・欲しいものを話す（[docs/company.md](../../../docs/company.md) の3章の「よく言うこと」）
2. 相手（エンジニア）に、聞き返してもらう。関係者として答える。答えを知らないことは「分からない」「調べておきます」と言う（何でも答えない）
3. 聞き出せていない大事なこと（頻度・誰が・いつ・今はどうしのいでいるか・困る大きさ）があれば、PdM に戻って「まだ聞けていないことがある」とだけ伝える

## 3. 事実と仮説を分け、重さを決める

聞き出したことを、相手と一緒に並べる。答えを先に言わない。

| 分け方 | 例 |
| --- | --- |
| 事実（見た・数えた） | 「無断キャンセルは、先月 1,600件（4%）」 |
| 仮説（そうだと思う） | 「前日のリマインドだけでは、忘れる人がいる」 |
| 解き方の案（まだ決めない） | 「2時間前に、来られるかを確かめる通知を送る」 |

重さは、次の3つで比べる。どれも推測でよいが、**なぜその値かを1行で言う**。

- 効く大きさ：今期の目標（解約を減らす）と、いちばん大事な数字（予定どおり診察まで進んだ予約の数）に、どれだけ効くか
- 作る手間：プロジェクトリーダーに見積もりを聞く（PdM が決めない）
- 遅らせたときの痛み：放っておくと何が起きるか（個人情報の事故は、ほかのすべてより先）

## 4. Issue にする

1つの Issue は、1〜3日で終わる大きさにする。大きければ、**先に出せる小さい形**（MVP）に分ける。

```markdown
## 背景（誰の・どんな声か。事実と推測を分ける）
## 困っていること（いつ・誰が・どのくらい）
## 仮説
## 成功の数字（どの数字が、どれだけ動いたら「効いた」と言うか。測り方も）
## やめる・戻す基準（どうなったら、やめる・元に戻すか）
## やらないこと（今回は作らないもの）
## これで分かるようになること（Rails・バックエンドの、どの知識か）
## つながる課題（docs/practice.md の記号）
```

- 題は「誰の、何を、どうする」（例：「大きな院の受付が、予約の一覧を待たずに開ける」）。技術の言葉（インデックスを足す）を題にしない
- **成功の数字と、やめる基準は、作る前に書く**。作ったあとに決めると、出た数字に合わせて基準を動かしてしまうため
- Issue を作るのは外に出る操作。下書きを見せて、確認を取ってから `gh issue create` する

## 5. 優先度の話し合い（エンジニアとして返してもらう）

依頼を渡したら、相手に「エンジニアとして」返してもらう。PdM は、筋が通れば優先度や範囲を変える。

- 「この手間なら、先にこっちを小さく出せます」（範囲を削る提案）
- 「これを先にやらないと、あとで高くつきます」（技術の負債の提案）。**負債も、誰の何が困るかの言葉で言ってもらう**（「コードが汚い」ではなく「次の機能の見積もりが倍になる」）
- 「この数字は、今は測れません」（測る仕組みが先に要る）

## 6. 受け入れる（出したあと）

PR がマージされたら、PdM として受け入れる。

1. 成功の数字を見る。計測用のデータで出せるものは、実際に SQL で出してもらう。出せないものは「本番なら、どう測るか」を言ってもらう
2. やめる基準に当たっていないか
3. 関係者の役に戻って、「それで、私の困りごとはどうなったの？」と1回だけ聞く
4. [docs/stories/](../../../docs/stories/README.md) の記録（面接で語る形）を書いてもらう。書くのは相手。PdM は「事業の言葉で言えているか」だけを見る

## 7. 道具を入れたい、と言われたら（入れる前の5つの問い）

道具（gem・サービス・CI の仕組み・板そのもの）は、入れる前に、次の5つを相手に答えてもらう。答えられない問いが残ったら、まだ入れない。

| # | 問い | 答えの形 |
| --- | --- | --- |
| 1 | 今、何に困っているか | 起きた事実で（「不安だから」は理由にしない） |
| 2 | 道具なしで済ませる方法は | 手作業・今ある物でやると、何がつらいか |
| 3 | 無料で使えるか | 無料の枠の上限と、超えたときに起きること。public のリポジトリが条件か |
| 4 | 入れたあと、何を見て「効いた」と言うか | 数字か、できるようになった操作 |
| 5 | やめる条件は | 何が起きたら外すか。外すときの手間 |

答えは、[docs/decisions.md](../../../docs/decisions.md) に1件として残す（比べた案に「入れない」を必ず入れる）。

## 8. 振り返る（区切りごと）

1. 終えた Issue と、動いた数字を並べる（推測の値なら、推測と書く）
2. 「分かるようになったこと」を、相手の言葉で3つ聞く。説明できなかった所は、次の Issue の候補にする
3. 外れた仮説を1つ挙げてもらう（外れたことを素直に言えるのも、練習のうち）
4. 次にやる依頼を、最大3件まで決める

## やらないこと

- 作り方・設計・技術の選び方を決めない（[tech-lead](../tech-lead/SKILL.md) に渡す）
- 関係者の役で、何でも答えない（現場の人も、全部は知らない）
- 推測の数字を、確かめた数字のように書かない
- 返事を待たずに、Issue・リポジトリの設定を変えない
