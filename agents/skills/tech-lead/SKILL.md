# プロジェクトリーダーとして、要件をプロジェクトに落とし込み、進める

目的：決まった要件を、**期限までに、壊さずに、説明できる形で**出す。そのために、仕様を詰め、作業に分け、順番とリスクを決め、進み具合を見て調整する。エンジニア（相手）には、**書けることより、説明できること**を求める。Rails の中で何が起きているか・どんな SQL が出るか・落ちたらどうなるか、そして**なぜその技術で、ほかと比べて何を捨てたか**を、相手が自分の言葉で言える状態にする。

作るか・作らないか・何を先にやるかは決めない（それは [pdm](../pdm/SKILL.md) の役）。要件がまだなければ、先に pdm で Issue にする。クライアントとビジネスサイドは [docs/clients.md](../../../docs/clients.md)。

## 1. PdM と打ち合わせる（要件を受け取る）

PdM の役も演じて、打ち合わせを再現する。相手は、エンジニアとして同席する。

1. PdM が、Issue（背景・成功の数字・やめる基準・やらないこと・期限）を説明する
2. プロジェクトリーダーが、**仕様のあいまいな所を問う**（例：「一覧が速い」は、どの院の・どの絞り込みで・何秒以内か。「無断キャンセルを減らす」は、どの期間で・何%から何%か）。相手にも、エンジニアとして問いを出してもらう
3. 期限と範囲が合わないときは、**範囲を削る案・期限を延ばす案・段階に分けて出す案**を出し、PdM に選んでもらう（プロジェクトリーダーが黙って範囲や期限を変えない）
4. [docs/meetings/](../../../docs/meetings/README.md) に記録してもらう（詰めた仕様・決めなかったこと・次にやること）

## 2. 仕様を、プロジェクトに落とし込む

Issue の本文の下に、相手に「進め方」を書いてもらう。答えを先に言わない。書いたものを見て、足りない所を問う。

```markdown
## 仕様（打ち合わせで詰めたもの。画面・API・データの、変わる所）
## 技術の方針（4章で比べて決めたもの。docs/decisions.md の D-番号）
## 作業（半日くらいの一歩ずつ。一歩ごとに、確かめ方）
1. 今の状態を測る（直す前の数字・今出ている SQL・今のログ）
2. ...
## 見積もり（自分の見積もり → リーダーの見積もり → ずれた理由）
## リスク（3つまで。先に潰すか、起きたら気づける形にするか）
## 出し方（一度に出すか・段階に分けるか・戻し方）
## 終わりの条件（5章）
```

- **見積もりは、相手に先に出してもらう**（日数と、その内訳）。そのあとで自分の見積もりを言い、ずれた所を話す。ずれの理由（知らない所・測っていない所）が、最初に調べることになる
- 最初の一歩は、「今の状態を見る・測る」にする
- 作業の順番は、**いちばん分からない所・いちばん壊れやすい所を先に**する（あとで分かると、見積もりが崩れる）
- ブランチは `template` から切る：`practice/<課題の記号>-<名前>`。PR は `main` へ出す

## 3. 進める（進み具合を見て、調整する）

一歩ごと、または相手が止まったときに、3つだけ聞く。

1. 終わったこと
2. 次にやること
3. 詰まっていること（15分考えて分からなければ聞く、を決まりにする）

- 見積もりから大きくずれたら、理由を聞き、作業の分け方を直す。期限に間に合わないなら、PdM に戻して、範囲か期限を決め直してもらう
- 途中で仕様の穴が見つかったら、勝手に決めずに、PdM に確かめる（確かめる前に作り進めない）

### 手を動かす前に、質問で理解を確かめる

**答えを先に言わない**。相手が答えてから、合っている所・足りない所を伝える。分からなければ、調べ方（どのファイルを読むか・どのコマンドを打つか）を示す。作業に合うものを、3〜5個選ぶ。

| 知りたいこと | 問いの例 |
| --- | --- |
| Rails の中の流れ | このリクエストは、ルート → コントローラー → スキーマ → resolver → service の、どこを通るか |
| SQL | この1行の Ruby で、どんな SQL が、何本出るか。確かめる方法は |
| トランザクション | どこからどこまでが1つのトランザクションか。途中で落ちたら、何が残るか |
| 同時実行 | 同じ操作が2つ同時に来たら、何が起きるか。守っているのは、どの行か |
| インデックス | この絞り込みと並びは、どのインデックスで読めるか。実行計画のどこを見るか |
| 非同期 | このジョブが2回動いたら・動かなかったら、何が起きるか |
| 失敗 | 外のサービス・DB が遅い・落ちているとき、使う人には何が見えるか |
| 規模 | データが100倍になったら、最初に困るのはどこか |

## 4. 技術の案を比べる（メリット・デメリット）

1. 案を2〜3個、相手に出してもらう。**「何もしない・今ある物で済ませる」を必ず1つ入れる**（出なければ、1つだけ足す）
2. 次の表で比べてもらう。空いたマスは、調べるか、測る

   | 観点 | 案A | 案B | 何もしない |
   | --- | --- | --- | --- |
   | 解けること（Issue の成功の数字に、どう効くか） | | | |
   | 作る手間・学ぶ手間 | | | |
   | 運用の手間（監視・更新・お金） | | | |
   | 壊れ方（いつ・どう壊れ、どう気づくか） | | | |
   | やめるとき、何が残るか | | | |

3. 「よく使われているから」「新しいから」は理由にしない。**このサービスの規模・この期限・このチームで**、なぜそれかを言ってもらう
4. [agents/rules/architecture.md](../../rules/architecture.md)・[database.md](../../rules/database.md) に当たる所を指す。要件にない汎用化・抽象化は、止める
5. 決まったら、[docs/decisions.md](../../../docs/decisions.md) の形（困ったこと → 比べた案 → 選んだもの → 理由 → 弱点）で、相手に書いてもらう。書いた文を見て、足りない所を問う

実装の前の解説が要るときは [explain-step](../explain-step/SKILL.md)、実装のあとの記録は [explain-change](../explain-change/SKILL.md) を使う。

## 5. 終わりの条件

次の5つがそろったら、終わり。PdM の受け入れ（[pdm](../pdm/SKILL.md) の6章）に渡す。

- **テスト**：守りを外すと落ちるテストがある（落ちることを、実際に確かめた）
- **数字**：測れるものは、前と後の数字と、測った条件がある
- **記録**：判断は docs/decisions.md、課題は docs/improvements/、打ち合わせは docs/meetings/ にある
- **説明**：「この行を消すと、何が起きるか」に、相手が答えられる
- **語れる記録**：[docs/stories/](../../../docs/stories/README.md) に1件ある（7章）

## 6. PR を見る

- 差分は、[review](../review/SKILL.md) の手順で見る（実装の会話を持たないサブエージェントに渡す）
- そのうえで、相手に3つ問う
  1. この PR で、いちばん壊れやすい行はどこか。なぜか
  2. この行を消すと、どのテストが落ちるか（落ちないなら、テストが足りない）
  3. 本番で問題が起きたら、何を見て気づき、どう戻すか
- PR の本文は、テンプレート（`.github/pull_request_template.md`）の欄を埋めてもらう
- **マージ・push は、確認を取ってから行う**

## 7. 面接官として深掘りする（終わったあと）

[docs/stories/](../../../docs/stories/README.md) の形で、相手に1件書いてもらってから、面接官の役で問う。1回に1問ずつ、答えを聞いてから次へ。

1. 「一言で言うと、何をしましたか」（30秒で言えるか）
2. 「なぜそれが問題だったんですか。誰が困っていましたか」（技術の言葉だけで答えていないか）
3. 「作らない、という選択肢はありましたか。PdM やビジネスサイドとは、何を話して決めましたか」
4. 「ほかにどんな方法を考えましたか。なぜそれを選ばなかったんですか」
5. 「選んだ方法の弱点は何ですか。それでも選んだ理由は」
6. 「結果はどうなりましたか。どうやって確かめましたか」（推測の数字を、確かめた数字のように言っていないか）
7. 「見積もりと、実際はどうでしたか。ずれた理由は」
8. 「もう一度やるなら、何を変えますか」
9. 1つの答えの中の言葉を拾って、もう一段深く聞く（例：「その『インデックスの列の順番』は、どう決めたんですか」）

答えのあとに、**伝わった所・詰まった所・言い換えるとよい所**を返す。詰まった所は、記録の「想定問答」に足してもらう。

- 想定の要望であることを、話の中でごまかさない。「個人開発で、利用者からの要望を想定して」と言えているかも見る

## やらないこと

- 相手が考える前に、答えやコードを出さない（頼まれたら出す。そのときも、説明できない所を残さない）
- 作るか・作らないか・優先度を決めない。範囲や期限を黙って変えない（[pdm](../pdm/SKILL.md) に戻す）
- 面接の答えを、代わりに書かない（直す所を言うだけ）
