## ルールを足す・変える

ルールは作業のたびに読まれるので、密度を保つ。

- 新しいルールは、次の3つをすべて満たすものだけ足す
  1. 自明でない：慣れた人でも、書かれていなければ間違える
  2. 繰り返す：同じ間違いが2回以上起きた（1回の作業での複数回を含む）
  3. 具体的：守り方が1つに決まる指示であり、漠然とした原則ではない
- 構造の説明（ディレクトリの中身、データの流れ）は書かない。コードを読めばわかり、すぐ古くなる。書くのは避けるべき罠である
- まず、同じカテゴリの既存ファイルに足せないかを考える。足せないとき、または1つのファイルが長くなりすぎたときだけ、新しいファイルに分ける
- 新しいファイルの名前は `<カテゴリ>-<内容>.md`（英小文字の kebab-case）にする
  - カテゴリは `architecture`・`testing`・`logging`・`database`・`api`・`quality`・`performance`・`ci`・`security` から選ぶ。合うものがなければ、足す理由を添えて新しいカテゴリを提案する
  - 例：`api-no-breaking-changes.md`（公開している API の互換性を壊さない）・`testing-timezone.md`（時刻と時間帯に依存させない）
- 1つの領域にしか効かないルールは、ファイルの先頭に `paths:` を付けて置く
- 各ルールには、守り方と一緒に「なぜ」を1行で書く。間違いやすい書き方と正しい書き方の例を、短く並べてよい
- ファイルを足したら、この目次の該当カテゴリに1行足す
- エージェントは通常の作業中にルールを直接書き換えない。追加案はレビュー報告に書き、足すかは人間が決める。足すときは、なぜ必要かを添えて専用のコミットにする
- 既存ルールの言い換えや明確化は、いつでも歓迎する

## 作業手順を呼び出す

| 作業 | スキル |
| --- | --- |
| 次に何を・なぜ・どの順でやるかを決める。Issue と板。道具を入れる前の5つの問い | [pm](skills/pm/SKILL.md) |
| 1つの Issue を、どう作るか・どこまでで終わりかを決める。質問で理解を確かめる。PR を見る | [tech-lead](skills/tech-lead/SKILL.md) |
| 実装の前に、次の一歩の解説を作って止まる | [explain-step](skills/explain-step/SKILL.md) |
| 実装のあとに、書いたコードを解説して、数字と一緒に記録する | [explain-change](skills/explain-change/SKILL.md) |
| 差分をレビューする（PR 前の自己点検を含む）、完了を判断する | [review](skills/review/SKILL.md) |
| 雛形を写した直後に、【記入】を順番に埋める | [harness-setup](skills/harness-setup/SKILL.md) |
| スキル・ルール・サブエージェントを、型どおりに足す | [harness-extend](skills/harness-extend/SKILL.md) |

## 相互レビューを依頼する

実装の会話を持たないサブエージェントに、差分と確かめたいこと（要件・その一歩の解説のページ）を渡す。実装の対話履歴や経緯は渡さない。

レビュー役には `isolation: worktree` を付けない。付けると、作業中の変更を持たない worktree が作られ、レビューしたい変更が見えなくなる。

## サブエージェントの一覧

定義は .claude/agents/ にある（Claude Code 向け）。

| 担当 | すること | 編集 |
| --- | --- | --- |
| [edge-case-reviewer](../.claude/agents/edge-case-reviewer.md) | 異常系・境界値の抜け | しない |
| [security-reviewer](../.claude/agents/security-reviewer.md) | 入力検証・認可・秘密情報 | しない |
| [refactorer](../.claude/agents/refactorer.md) | テストを Green に保ったまま、1変更ずつ直す | する |

- edge-case-reviewer は Bash で差分を取得する。security-reviewer には呼び出し元から差分を渡す
- refactorer も、コミット・push はしない
- 段階4より前は、認可のまとめがまだない（わざと後回しにしている）。security-reviewer の指摘のうち、後回しにしているものは、直さずに記録だけする
