# ジュニアからミドルへのロードマップ

このリポジトリで練習する目的の1つは、**DB・バックエンドの理解と、改善した経験を、面接で語れる形で積むこと**。そのための観点と段階を、ここに置く。期間は決めない（使える時間が決まっていないため）。段階ごとの**終わりの条件**で進み具合を見る。

PdM（[pdm](../agents/skills/pdm/SKILL.md)）は要望を選ぶときに、プロジェクトリーダー（[tech-lead](../agents/skills/tech-lead/SKILL.md)）は段階の終わりの深掘りで、ここを使う。

## 1. ミドルエンジニアの姿

> **1つの機能を、要望から出したあとの確認まで、1人で回せる。判断の理由を、比べた案と一緒に説明できる。困ったときは、早く・具体的に相談できる。**

## 2. 8つの観点

| # | 観点 | ジュニア | ミドル |
| --- | --- | --- | --- |
| 1 | 要望を理解する | 言われた仕様を作る | 困りごとを聞き返し、事実と仮説を分け、「作らない」も提案できる |
| 2 | 設計と判断 | 動く形を1つ作る | 案を2つ以上（何もしないを含めて）比べ、弱点も言える |
| 3 | DB と SQL | ORM の書き方を知っている | 出る SQL が分かり、実行計画を読み、インデックスとトランザクションを決められる |
| 4 | 失敗への備え | うまくいく道を作る | 二重送信・同時更新・外部サービスの失敗・ジョブの再実行を、先に考えられる |
| 5 | 調査と障害対応 | 言われた所を直す | ログと数字から原因に辿り着き、再発を防ぐテストと報告を書ける |
| 6 | 見積もりと報告 | 終わったら報告する | 先に見積もり、ずれそうなら早く言い、範囲を削る案を出せる |
| 7 | レビュー | レビューを受ける | 他人の PR の、壊れやすい所を具体的に指摘できる |
| 8 | 語る力 | やったことを話す | 誰の何が困っていて、なぜその方法で、何が良くなったかを話せる |

いちばん伸ばしたいのは **1・3・4・5**。

## 3. 段階

| 段階 | 主に伸ばす観点 | 要望（[clients.md](clients.md)）と課題（[practice.md](practice.md)） | 終わりの条件 |
| --- | --- | --- | --- |
| **1. 測ってから直す** | 1・3・6 | R-1（一覧が重い）→ E-1・E-2 | 遅い一覧を再現し、実行計画を読み、インデックスを決めて、前と後の数字を出す。見積もりと実際の差を言える |
| **2. 原因を突き止める** | 5・3 | R-3（メールが来ない）・R-5（別の院の予約が見えた）→ C-1・C-2・C-4 | 仕込まれた不具合を、答えを聞かずに見つけて直す。障害の報告を書く |
| **3. 失敗に備える** | 4・2 | R-2（無断キャンセル）→ D-1・D-2 | ジョブの失敗・重複・遅れを起こして、守り方を決める。成功の数字を作る前に決める |
| **4. 判断し、人のコードを見る** | 1・2・7 | R-7（CSV）・R-8（ぶつかる要望）→ B-1・B-2 | 「作らない」か「別の形」を、打ち合わせで決めて記録する。レビュー役として PR を見る |

各段階の終わりに、プロジェクトリーダーが面接官の役で、8つの観点を確かめる（[stories/](stories/README.md) を元に深掘りする）。

### 毎回くり返す型

> 要望を聞く → 事実と仮説を分ける → **測る** → 案を比べる → 作る → **測る** → 語れる記録にする

## 4. フロントエンドのミドルに要る技能

| # | 分野 | ミドルの目安 | このリポジトリで練習できる所 |
| --- | --- | --- | --- |

| 2 | サーバーで描く・ブラウザで描く | App Router のサーバーの部品とブラウザの部品の境界を、理由つきで引ける。SSR・SSG・ISR・ストリーミング（Suspense）の使い分けと、Next.js のキャッシュの効き方を説明できる。Pages Router との違いも言える | [frontend.md](frontend.md) の「描く場所の分け方」・`PreloadQuery` の比較 |
| 3 | データの取得とキャッシュ | Apollo のキャッシュの正規化・`typePolicies`・ページングのまとめ方・`fetchPolicy` を説明できる。mutation のあと一覧が古くなる理由と直し方、楽観的な更新の危うさも言える | 予約・キャンセル後のキャッシュの捨て方・医師の予定の取り直し |
| 4 | 状態の置き場所 | サーバーの状態・URL・フォーム・画面の中・アプリ全体に分けて置ける。状態管理の道具を入れない判断も説明できる | [frontend.md](frontend.md) の状態の5種類 |
| 5 | フォームと二重送信 | フォームの検証とサーバーの検証の役割を分けられる。二重送信・送信中の操作・失敗したあとの見せ方を設計できる | 予約の確認の窓 |
| 6 | アクセシビリティ | 意味のある要素・キーボード操作・ダイアログのフォーカス・色のコントラストを守れる。テストで `getByRole` を使う理由を言える | 確認の窓・3つの画面 |
| 7 | 認証とセキュリティ | Cookie（HttpOnly・SameSite・Secure）・CSRF・XSS・CORS の意味を知っている。トークンを localStorage に置かない理由と、同じオリジンで中継する理由を説明できる | D-017（中継・Origin の確認） |
| 8 | 部品の設計 | データを取る部品と描くだけの部品を分けられる。props が増え続けたら、組み合わせに直せる。デザインのトークンで見た目をそろえられる | `packages/ui`・`packages/web-kit` |
| 9 | 型の設計 | 判別できる共用体・`unknown`・`satisfies` を使い分けられる。GraphQL から型を作り、手で書く型を減らせる | GraphQL Code Generator・fragment masking |
| 10 | テストの戦略 | どの層で何を守るかを決められる。MSW の使いどころと、不安定なテストの直し方を言える | [frontend.md](frontend.md) の「テストをどの層で守るか」 |
| 11 | 出したあとの運用 | 画面のエラーを集める（ソースマップを含む）。機能フラグで段階的に出し、悪ければ戻す。ブラウザの対応範囲を決められる | C-1 |
| 12 | 配る仕組み | CDN・キャッシュのヘッダー・画像とフォントの最適化を説明できる。静的に出せる所と、毎回描く所を分けられる | ビルドの結果 |

## 5. 深掘りされたときの、共通の7つの観点

経験を話すと、次の7つで深掘りされることが多い。どの記録（[stories/](stories/README.md)）も、この7つに答えられるようにする。

| 観点 | 聞かれ方の例 |
| --- | --- |
| 自分の役割 | 「あなたが決めた所と、チームで決めた所は」 |
| 何が困っていたか | 「誰が、どのくらい困っていましたか」 |
| 比べた案 | 「ほかに何を考えましたか。なぜ選ばなかったんですか」 |
| 弱点 | 「選んだ方法の弱点は。どう補いましたか」 |
| 結果と測り方 | 「どうやって確かめましたか。その数字はどう測りましたか」 |
| 失敗 | 「うまくいかなかった所は」 |
| 今ならどうする | 「今やるなら、何を変えますか」 |

覚えていない数字は、作らない。「正確な数字は手元にありませんが、だいたい〇〇でした。測り方は△△でした」と言えれば十分。作った数字は、2つ目の問いで崩れる。

このリポジトリの外の経験（実務）の深掘りの問いは、公開しない。手元の `private/`（Git の管理外）に置く。
