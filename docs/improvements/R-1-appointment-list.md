# R-1. 大きな院で、予約の一覧（いつからでも）が遅い

- 日付: 2026-11-23 ／ 要望: [clients.md](../clients.md) の R-1 ／ 課題: E-1 ／ 関係する判断: [D-004](../decisions.md)（組の外部キー）・[D-019](../decisions.md)（計測用のデータ）

## 1. 症状

医師30人の院の受付から、「電話で前の予約や先の予約を聞かれたとき、期間を消して『いつからでも』にし、先生で絞ると、くるくるが長い（5〜10秒）」という声が届いた（想定の要望）。受付の3人とも感じていて、遅いときは折り返しの電話にするか、紙の台帳で探している。

## 2. 測った

計測用のデータ（`bin/rails bulk:load`。予約100万件、うち医師30人の院に約28万件）で、事務スタッフの入口に、画面と同じクエリ（1ページ20件）を5回ずつ送った。時間は curl の全体の時間、内訳は Rails のログ（`Completed … ActiveRecord: …`）、SQL は `EXPLAIN (ANALYZE, BUFFERS)` で読んだ。

| 受付さんの操作 | API 全体（5回） | 1本目の SQL |
| --- | --- | --- |
| 今日から | 40〜160 ms | — |
| いつからでも | **200〜500 ms** | 1回目 430 ms・2回目以降 約150 ms |
| いつからでも＋先生 | 約45 ms | 0.2 ms |
| 上の続き（1〜6ページ目） | 約40 ms | — |

**受付さんの仮説と、測った結果は違った**。先生で絞るとむしろ速く、遅いのは「いつからでも」で先生を選ぶ前の1回目だった。時間も、手元では最大0.5秒で、5〜10秒ではない（本番のデータの量・同時に使う人・画面の描画やネットワークの時間は、ここでは再現していない）。

## 3. 原因

「いつからでも」の SQL は、絞る列（予約の `clinic_id`）と並べる列（枠の `starts_at`）が別の表にある。合う索引がないので、DB は院の予約を全部（約28万件）と枠を全部（約111万件）読んで突き合わせ（Parallel Hash Join）、作業用のディスクも使って並べ替え、上の20件を取っていた（`Seq Scan`・`Rows Removed by Filter: 238991`・`temp written=8392`）。

先生で絞ったときは、枠の索引（`doctor_id, starts_at`）を時刻の順にたどり、27行で止まれていた。

## 4. 直した

予約と枠の医療機関は、組の外部キー（D-004）で必ず同じになる。そこで、スタッフの一覧には「**枠の医療機関も同じ**」という条件（`slots.clinic_id = 院`）を足した（`app/queries/appointments/list_query.rb`）。結果は変わらず、DB が枠の索引（`clinic_id, starts_at, id`。すでにある）を時刻の順にたどれるようになる。

比べた案:

| 案 | 良い所 | 弱い所 |
| --- | --- | --- |
| **枠の医療機関の条件を足す（選んだ）** | 1行。表も索引も増えない。今ある索引を使う | 「同じ値の条件を2回書く」理由が、コードだけでは分かりにくい（コメントで書いた） |
| 予約の表に、枠の開始時刻を写して持ち、`(clinic_id, slot_starts_at, id)` の索引を作る | 予約の表だけで絞って並べられる | 枠の時刻を変えたら、写しも直す必要がある。列と索引が増え、100万件の表の定義を変える（E-3 の手順が要る） |
| 何もしない | 手間がない | データが増えるほど、そのまま遅くなる（読む行数が院の予約の数に比例する） |

## 5. 数字

| | 前 | 後 |
| --- | --- | --- |
| 1本目の SQL（2回目以降） | 155 ms | **1 ms** |
| 読んだ行（枠） | 約111万（全部） | 31 |
| 共有バッファの読み（hit＋read） | 26,681 | 138 |
| API 全体（いつからでも、2〜5回目） | 198〜274 ms | **34〜42 ms** |

測った条件: 手元の Docker（PostgreSQL 18.7）・計測用のデータ（予約100万件・院の予約約28万件）・1人で操作・1ページ20件。

## 6. 再発防止

- `test/queries/appointments_list_query_spec.rb`: スタッフの一覧の SQL が枠の医療機関で絞っていること（条件を外すと落ちることを確かめた）と、絞っても返る予約が変わらないこと
- 結果の正しさ（医療機関ごとの分離・絞り込み・続きの読み込み）は、`test/graphql/appointments_query_spec.rb` がそのまま守る

## 残したこと

- 受付さんの「5〜10秒」は、手元では再現していない。直したあと、受付さんにもう一度聞く（PdM の受け入れ）
- ダッシュボードの集計（`Dashboards::DailyQuery`）も同じ形（予約の医療機関で絞り、枠の時刻で範囲を取る）。R-4 で測る
