## 書く形

```markdown
## D-番号. 題（何を決めたか）

- 日付: YYYY-MM-DD ／ 段階: N ／ 状態: 決定
- 困ったこと: 何が起きたか・何を決める必要があったか（数字があれば書く）

  - 案A: 良いところ ／ 弱いところ

- 弱点・やめる条件: 何が起きたら見直すか
- 確かめた数字: 前 → 後（測り方も）
```

## D-001. 構成と技術の選定

- 日付: 2026-11-17 ／ 段階: 0 ／ 状態: 決定
- 困ったこと: バックエンドとフロントエンドの設計を、自分で作って確かめる題材と構成を決める
- 比べた案:
  - 案A: 手本にする構成と同じ（Rails＋graphql-ruby＋PostgreSQL、Next.js＋Chakra UI＋Apollo Client）: よく使われる組み合わせを、一から組んで理解できる ／ 新しい道具は増えない
  - 案B: 別の構成（Go や Hono など）: 幅は広がる ／ 道具の学習に時間を使い、設計の理由まで届きにくい
- 選んだもの: 案A。ただし、Next.js は App Router、Chakra UI は今の最新、N+1 は graphql-ruby 標準の Dataloader、ジョブは Solid Queue にして、手本の構成（Pages Router・GraphQL::Batch・Delayed::Job）と比べる
- 理由: 目的は道具を増やすことではなく、設計の理由を説明できるようにすること。違う所は、比べることで理由が分かる
- 弱点・やめる条件: App Router は、Apollo Client・Chakra UI と境界の引き方が難しい。段階2で測って、面倒が利点を上回るなら、取り方を見直す
- 確かめた数字: まだない

詳しい表は [roadmap.md](roadmap.md) の 2章・3章。

## D-002. 進め方を「最初からきちんと作る」に変える

- 日付: 2026-11-17 ／ 段階: 0 ／ 状態: 決定
- 困ったこと: 「素朴に作る → 困ることを起こす → 測る → 入れる」の順番だと、動くものができるまでが遠い。このリポジトリでは、まず動くものを、きちんとした設計で作りたい
- 比べた案:
  - 案A: 前のまま（素朴に作って、段階ごとに課題を起こして直す）: 入れる前の状態と、前と後の数字が残る ／ 動くものができるまでに、解説と測定で何度も止まる
  - 案B: 最初からきちんと作る（制約・N+1 の対策・インデックス・カーソル・認可・層の分割・エラーの設計を、機能と一緒に入れる）: 動くものが早くでき、設計を通しで見られる ／ 「前」の数字が取れない
  - 案C: 手戻りが大きいもの（DB の制約・認可）だけ最初から入れる: 中間 ／ どこまで入れるかの線引きが毎回要る
- 選んだもの: 案B。範囲は、まず段階1（ログイン・診療枠・予約・キャンセル・予約の一覧）まで。解説で止まらずに作り、解説と記録は動いたあとにまとめて作る
- 理由: このリポジトリの主題は、アーキテクチャを通しで組むこと。名前も clinic-architecture に変えた
- 弱点・やめる条件: 「入れなかったら何が起きるか」を体験しない。代わりに、守れていることをテストで確かめ（同時に20リクエスト・クエリの本数の上限・他院の ID）、理由をこの記録に書く。100万件での実行計画は、まだ見ていない
- 確かめた数字: まだない

## D-003. テーブル設計の初版

- 日付: 2026-11-18 ／ 段階: 1 ／ 状態: 決定
- 困ったこと: 医療機関・患者・スタッフ・診療枠・予約を、どんな表・型・制約で持つかを決める
- 決めたこと（マイグレーションは `apps/api/db/migrate/`）:
  - **主キーは bigint の連番**。比べた案は UUID（番号から件数や次の番号を推測されない ／ 大きく、インデックスの局所性が悪い）。番号を推測されても、認可（D-006）で見られないので、連番にした
  - **患者とスタッフは別の表**（`patients`・`staff_members`）。患者は医療機関に属さず、スタッフは1つの医療機関に属する。入口（ログイン）も別。比べた案は1つの `users` 表（ログインが1つで済む ／ `clinic_id` が患者だけ NULL になり、「スタッフには必ず医療機関がある」を NOT NULL で守れない）
  - **医師と事務スタッフは同じ表**で、`role` の列（CHECK つき）で分ける。持つ項目が同じため
  - **予約の状態は1つの列**（`status`。CHECK で6つの値に限る）。フラグの列を並べない。「キャンセル」と `canceled_at` が片方だけにならないことも CHECK で守る
  - **日時は timestamptz**（要件 R8）。`config/initializers/postgresql_timestamptz.rb`
  - **医療機関の ID を、枠と予約の両方に持つ**（要件 R7）。さらに、`(slot_id, clinic_id)` と `(doctor_id, clinic_id)` を**組の外部キー**にして、「予約の医療機関は、枠の医療機関と同じ」「枠の医師は、その医療機関の人」を DB で守る。比べた案は、親をたどる（列が減る ／ 一覧のたびに結合が要り、絞り込みの条件を付け忘れやすい）
  - **同じ医師の枠の時間は重ならない**（要件 R2）を、排他制約（`EXCLUDE USING gist (doctor_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`）で守る。比べた案は UNIQUE（医師・開始時刻）だけ（単純 ／ 9:00〜9:30 と 9:15〜9:45 が両方入る）。UNIQUE も、開始時刻の順で読むインデックスを兼ねて置いた
- 弱点・やめる条件: 排他制約は `btree_gist` の拡張が要る。インデックスの列の順番は、まだ実行計画で確かめていない（100万件を入れてから見直す）
- 確かめた数字: 制約ごとに、検証を飛ばして直接 DB に書いても入らないことを、`spec/models/constraints_spec.rb`（11件）で確かめた

## D-004. 二重予約をどう防ぐか（要件 R1）

- 日付: 2026-11-18 ／ 段階: 1 ／ 状態: 決定
- 困ったこと: 「空いているか確かめてから、予約を入れる」は、確かめたあとに他の人が入れると破れる。同時に来ても、1つの枠に有効な予約は1件にしたい
- 比べた案:
  - 案A: **部分 UNIQUE**（`appointments(slot_id) WHERE status <> 'canceled'`）: アプリのコードを通らない書き込みでも守れる。ロックを持たないので速い。キャンセルした枠をもう一度予約できる ／ 「埋まっている」が、例外（`RecordNotUnique`）で分かる。「有効」の定義（どの状態を除くか）がインデックスの定義に入るので、変えるときはインデックスを作り直す
  - 案B: 枠の行をロック（`SELECT ... FOR UPDATE`）してから確かめて入れる: 読みやすい。定員が2人以上でも使える ／ ロックを取り忘れた書き込みは守れない。待ちが出る
  - 案C: 枠の側に状態を持つ（`slots.status = 'booked'` への条件付き更新）: 空き枠の検索が速い ／ 同じ事実（予約がある）を2か所に持ち、ずれる
- 選んだもの: 案A。`Appointments::Book` は、確かめずに INSERT して、UNIQUE に当たったら「すでに埋まっています」（`SLOT_TAKEN`）を返す
- 理由: 定員は1人で、これは「同時実行で破れる不変条件」。DB の制約で守るもの（[database.md](../agents/rules/database.md) の表）
- 弱点・やめる条件: 定員が2人以上になったら、UNIQUE では書けない（案B か、数を持つ列に変える）。無断キャンセル（`no_show`）は有効として数えているので、その枠は予約できないまま（時刻を過ぎているので問題にならない）
- 確かめた数字: 同じ枠に、同時に20件（スレッド20本・接続20本）の予約を送るテスト（`spec/services/appointments/book_spec.rb`）。UNIQUE を外すと **20件中20件が成功**、ある状態では **20件中1件が成功・19件が SLOT_TAKEN**（手元の Docker・PostgreSQL 18.7・テスト用の DB。[K1](improvements/K1-double-booking.md)）

## D-005. バックエンドの層の分け方

- 日付: 2026-11-18 ／ 段階: 1 ／ 状態: 決定
- 困ったこと: mutation に処理を書いていくと、認可・状態の確認・トランザクションが入口に混ざり、GraphQL を通さないとテストできなくなる
- 比べた案:
  - 案A: Rails の標準に寄せる（モデルに業務の処理を持たせる）: ファイルが少ない ／ モデルが太り、1つの操作の流れが複数のモデルに散る
  - 案B: **入口・業務の処理・読み取り・認可・モデルに分ける**: 1つの操作が1つのクラスで読める。GraphQL を通さずにテストできる ／ ファイルが増える。小さな操作でもクラスを作る
- 選んだもの: 案B
  - 入口 `app/graphql/`（resolver・mutation）: 入力 → ログインの確認 → 呼ぶ → 結果を形にする、だけ
  - 業務の処理 `app/services/<機能>/`: 1つの操作 = 1クラス。結果は `Result`（成功の値か、`UserError` の並び）
  - 読み取り `app/queries/<機能>/`: 一覧と空き枠の SQL
  - 認可 `app/policies/`、モデル `app/models/`（関連・検証・値の一覧だけ）
  - DB も時計も読まない決まりは、別のモジュールに出す（`Appointments::CancellationRule`・`Slots::Schedule`）。今の時刻は、入口で1回だけ決めて、引数で渡す
- 理由: 「最初からきちんと作る」（D-002）ので、太ってから分けるのではなく、最初から置き場を決めた。機能ごとのフォルダ（`appointments`・`slots`・`auth`）は、[architecture.md](../agents/rules/architecture.md) の「機能ごとに縦に切る」を、Rails の `app/` の中でやった形
- 弱点・やめる条件: 機能どうしの境界（予約が枠の表を直接読む、など）は、まだ止めていない（段階6の Packwerk）。操作が増えて似たクラスが並んだら、共通の形を見直す

## D-006. 認可をどの層に置くか

- 日付: 2026-11-18 ／ 段階: 1 ／ 状態: 決定（要件 13章の M5）
- 困ったこと: ID を変えると、ほかの医療機関・ほかの患者の予約が取れる（IDOR）、を起こさない。認可の条件を、あちこちに書かない
- 比べた案:
  - 案A: graphql-ruby の仕組み（型の `authorized?`）だけ: 項目を取る所で必ず通る ／ 一覧では、取ってから1件ずつ弾くので、件数とページングがずれる。業務の処理（キャンセル）からは使えない
  - 案B: Pundit などの gem: 型が決まっている ／ この規模では、自分で書くクラス2つと変わらない
  - 案C: **ポリシーのクラスを自分で書き、3か所から使う**
- 選んだもの: 案C（`app/policies/appointment_policy.rb`・`slot_policy.rb`）
  1. **絞り込み**（`AppointmentPolicy.scope(user)`）: 一覧も1件の取得も、見られる行だけの relation から始める。見られない行は「見つからない」になり、あるかどうかも分からない
  2. **業務の処理**: `scope` から探して（なければ `NOT_FOUND`）、操作できるかを確かめる（できなければ `NOT_PERMITTED`）
  3. **型の `authorized?`**（`AppointmentType`・`PatientType`）: ほかの型からたどって届いたときの、最後の守り
  - ログインの確認は、resolver と mutation の入口（`Authentication`）。ログインが要らないものだけ `allow_guest!` と書く
- 理由: 要件の4章の表を、ポリシーの1か所に書ける。一覧は SQL の条件で絞るので、件数とページングがずれない
- 弱点・やめる条件: 医療機関・医師・枠の型には `authorized?` がない（ログインしていれば誰でも見られる情報）。型が増えて、付け忘れが心配になったら、既定で断って、見せる型だけ許す形に変える
- 確かめた数字: 役割ごとの「見える・キャンセルできる」を、8通りの人で確かめた（`spec/policies/appointment_policy_spec.rb`）。ほかの医療機関・ほかの患者の ID を指定するテストは、一覧・キャンセル・枠の作成で計9件。型の `authorized?` が断る道を通るテストは、まだない（今は、先に絞っているので届かない）

## D-007. GraphQL のエラーをどう返すか

- 日付: 2026-11-18 ／ 段階: 1 ／ 状態: 決定
- 困ったこと: 画面で、エラーの種類（すでに埋まっている・入力の誤り・ログインが切れた・サーバーの不具合）を見分けて、出し方を変えたい
- 比べた案:
  - 案A: 全部を GraphQL の `errors` に入れ、`extensions.code` で見分ける: 入口が1つ ／ 型が付かない。項目ごとの入力のエラーを運びにくい
  - 案B: **使う人が直せるものは mutation の結果の中（`errors { code message field }`）、それ以外は GraphQL の `errors`**: 結果に型が付き、画面がコード（enum）で分岐できる ／ 見る場所が2つになる
- 選んだもの: 案B（要件の9章のとおり）
  - 結果の中: `ErrorCode`（`apps/api/lib/error_code.rb` が一覧の正）。`INVALID_INPUT`・`SLOT_TAKEN`・`NOT_FOUND`・`NOT_PERMITTED` など
  - GraphQL の `errors`: `UNAUTHENTICATED`（ログインしていない）・`BAD_REQUEST`（壊れたカーソル）・`INTERNAL`（想定していないエラー。中身は出さず、ログにだけ残す）
  - 画面: 結果の中のエラーは各フォームが出し、GraphQL の `errors` と通信の失敗は Apollo の `ErrorLink` の1か所（今は `packages/web-kit/src/apollo.ts`）で受ける
- 弱点・やめる条件: query には結果の入れ物がないので、query の「見つからない」は null か GraphQL の `errors` になる。HTTP の状態は全部 200 なので、エラー率を測るには別の仕組みが要る（段階6）

## D-008. 一覧のページングと N+1

- 日付: 2026-11-18 ／ 段階: 1 ／ 状態: 決定
- 困ったこと: 一覧を、深いページでも遅くならず、途中で行が増えても同じ行が2回出ない・抜けない形で返したい。行の数だけ SQL が出るのを防ぎたい
- 比べた案（ページング）:
  - 案A: graphql-ruby の標準の Connection（カーソルの中身は「何件目か」。SQL は OFFSET）: 何も書かなくてよい ／ 深いページほど読み捨てる行が増える。途中で行が増えるとずれる
  - 案B: **並びのキーをカーソルにする**（keyset。`WHERE (starts_at, id) > (?, ?)`）: 深さに関係なく速い。ずれない ／ 前へ戻る・何ページ目へ飛ぶ、ができない。自分で書く
- 選んだもの: 案B（`apps/api/lib/pagination/keyset_connection.rb`）。並びは「枠の開始時刻 → id」。id を足して、同じ時刻の行でも順番が決まるようにした。1件多く読んで、続きがあるかを知る（件数を数える SQL を出さない）。1回に読めるのは50件まで
- 比べた案（N+1）:
  - 案A: 一覧の SQL で、関連を全部まとめて読む（`includes`）: 単純 ／ 画面が要らない関連まで読む。型が増えるたびに一覧の側を直す
  - 案B: **Dataloader**（項目を取る所で、同じ種類の読み込みをためて1回にする）: 要る項目だけ読む ／ 仕組みの理解が要る
- 選んだもの: 案B（`app/graphql/sources/`）。Bullet を開発（ログ）とテスト（例外）で有効にした
- 弱点・やめる条件: GraphQL::Batch との比較（[roadmap.md](roadmap.md) の2章）は、まだしていない。100万件での実行計画も、まだ見ていない
- 確かめた数字: 予約の一覧は、3行でも15行でも **SQL が5本**（予約と枠の結合・枠・患者・医師・医療機関）。空き枠は **2本**。読んでいる途中で前のほうに予約が増えても、重複も抜けもない（`spec/graphql/appointments_query_spec.rb`）

## D-009. 認証と、画面から API への道

- 日付: 2026-11-18 ／ 段階: 1 ／ 状態: 決定
- 困ったこと: ブラウザ・Next.js のサーバー・Rails の3つのあいだで、ログインをどう運ぶか
- 比べた案:
  - 案A: ブラウザから Rails へ直接送る（別のオリジン）: 中継がない ／ CORS の設定と、別オリジンへ Cookie を送る設定が要る
  - 案B: **ブラウザは、画面と同じオリジンの `/graphql` に送り、Next.js が Rails へ中継する**（`next.config.ts` の rewrites）: 同じオリジンなので、Cookie がそのまま使え、CORS が要らない。Rails の場所をブラウザに見せない ／ 中継が1つ挟まる
- 選んだもの: 案B。認証は Cookie のセッション
  - ログインのときに、セッションを作り直す（ログイン前に仕込まれたセッションを使わせない）
  - CSRF の守りは3つ: Cookie の SameSite=Lax・Origin の確認（画面のオリジン以外は 403）・JSON だけを受ける（415）
  - サーバーの部品（レイアウト）は、ブラウザの Cookie をそのまま Rails に渡して、ログインしている人を聞く（今は `packages/web-kit/src/server.ts` と、各アプリの `lib/viewer.ts`）。画面の出し分けのためだけで、データを守るのは Rails の認可
- **セッションは DB に置く**（2026-11-18 に変更。`sessions` の表）。Cookie には合言葉（トークン）だけを入れ、DB にはそのハッシュ・持ち主・期限（12時間）を持つ。ログアウトで行を消すので、控えておいた Cookie の値も、その場で使えなくなる（要件の「すぐ無効にできる」）。前は Cookie の中だけに持っていて、ログアウトしても期限まで使えた（レビューの指摘）
- 弱点・やめる条件: リクエストのたびに、セッションを DB から1回読む。期限が切れた行を消す処理は、まだない（たまるだけで、ログインには使えない）。アプリや外部のクライアントが増えたら、トークンを考える

## D-010. フロントエンドの層・状態の置き場・mutation のあとのキャッシュ

- 日付: 2026-11-18 ／ 段階: 1 ／ 状態: 決定
- 決めたこと:
  - **層**: `app/` → `features/<機能>/` → `lib/`・`packages/ui`。向きは、最初から ESLint（`import/no-restricted-paths`）で止める。features どうしも直接 import しない（[frontend.md](frontend.md) の1章）
  - **描く場所**: サーバーの部品は、レイアウトとログインの確認だけ。データを取る所は、ブラウザの部品（Apollo Client の `useQuery`）。サーバーで先にデータを取って描く形（`PreloadQuery`）は、まだ入れていない（表示速度を測ってから決める）
  - **Chakra UI と App Router**: Emotion のスタイルを、`useServerInsertedHTML` でまとめて流す（今は `packages/web-kit/src/emotion-registry.tsx`）。入れないと、サーバーの HTML とブラウザの描画が食い違う（Hydration failed）
  - **状態の置き場**: サーバーの状態は Apollo のキャッシュ、絞り込みとタブは URL、フォームは React Hook Form＋Zod、ログインしている人は Context（サーバーで確かめた値を配る）
  - **型**: スキーマ（今は `apps/api/schema/` の3つ）とクエリから作る（client-preset）。行に要る項目は、行を描く部品の隣の fragment で決める
  - **mutation のあとのキャッシュ**（操作ごと）:

    | 操作 | 直し方 | 理由 |
    | --- | --- | --- |
    | 予約する | 予約の一覧のキャッシュを捨てる（次に開いたときに取り直す）。失敗（すでに埋まっている）のときは、空き枠を取り直す | 新しい予約が、どの絞り込みの一覧のどこに入るかを、画面の側で決めるのは難しい |
    | キャンセルする | 返ってきた予約（id・状態）で、行が自動で新しくなる。空き枠のキャッシュは捨てる | 行は同じ id なので、正規化されたキャッシュに任せられる |
    | 診療枠を作る | 空き枠のキャッシュを捨てる | 増えた枠を、画面の側で並べ直さない |

  - **楽観的な更新は入れない**（予約・キャンセルとも、結果を待ってから画面を変える）。同じ枠にほかの人が先に入ることがあり、「できた」と見せてから取り消すほうが害が大きい。送っているあいだは、ボタンを押せなくする
- 弱点・やめる条件: 絞り込み（状態＝予約済）で見ている一覧でキャンセルすると、その行は「キャンセル」の表示で残る（次に取り直すまで）。一覧を捨てて取り直す形は、通信が1回増える

## D-011. 予約の変更・代理の予約・枠を閉じる（同時に来たときの守り方）

- 日付: 2026-11-18 ／ 段階: 3 ／ 状態: 決定
- 困ったこと: 予約の変更は「新しい枠を押さえる」と「前の枠を空ける」を、片方だけ成功させたくない。枠を閉じるのと予約が同時に来ると、「閉じた枠に予約が入っている」になりうる
- 決めたこと:
  - **予約の変更は、1つの UPDATE**（`appointments.slot_id` の付け替え）。予約の行を作り直さないので、押さえると空けるが同時に起きる。新しい枠が埋まっていれば、二重予約と同じ部分 UNIQUE に当たり、前の枠のまま残る。比べた案は「前の予約をキャンセルして、新しい予約を作る」（履歴が残る ／ 2つの書き込みを1つのトランザクションに入れる必要があり、ロックの順番を考えることになる）
  - **デッドロック**: 2人が互いの枠へ同時に変えようとすると、UNIQUE の確認が相手の結果を待ち合う。PostgreSQL が片方を止めるので、止められた側には `CONFLICT`（もう一度試してください）を返す。自動のやり直しは入れていない（やり直しても、相手の枠は埋まっている）
  - **枠を閉じる**: 閉じる側は枠の行を `FOR UPDATE`、予約と変更の側は `FOR SHARE` で読んでから確かめる。予約どうしは待たず、閉じる処理とだけ待ち合う
  - **代理の予約**: 事務スタッフが、患者をメールアドレスで指定して入れる。誰が入れたかを `booked_by_staff_member_id` に残す。変更できるかの決まりは、キャンセルと同じ（`CancellationRule`）
- 弱点・やめる条件: 変更の履歴（前はどの枠だったか）は残らない（監査ログの段階で考える）。代理の予約は、事務スタッフに「そのメールアドレスの患者が登録されているか」が分かる
- 確かめた数字: 10人が同じ空き枠へ同時に変えると、成功は1人。互いの枠への変更を20回繰り返しても、枠に2件は入らず、例外も外へ出ない。閉じるのと予約を同時に15回送ると、毎回どちらか片方だけが成功する。予約の側の `FOR SHARE` を外すと、3回走らせて3回とも「両方成功」が出た。変更の側の `FOR SHARE` を外しても、同じく「両方成功」が出た（手元の Docker・テスト用の DB）

## D-012. 受付〜診察の状態の進め方と、会計

- 日付: 2026-11-18 ／ 段階: 5 ／ 状態: 決定（決済は作らない、と決めた）
- 困ったこと: 状態の遷移（受付・開始・終了・無断キャンセル）が、2回押された・定期の処理と同時に来た、で壊れないようにする。会計の金額が、あとから変わらないようにする
- 決めたこと:
  - **状態を進めるのは、条件付きの更新1つ**（`Appointments::Transition.move`。`WHERE status = 前の状態`）。行を読んでから書くのではなく、「今もその状態なら」を更新の条件に入れるので、進むのは1回だけ。比べた案は、行をロックしてから確かめて書く（読みやすい ／ ロックを取り忘れた経路は守れない。1件の更新には大げさ）
  - **診察を終えると、会計の下書きを同じトランザクションで作る**。「診察は終わったのに会計がない」を起こさない。会計は予約に1つ（UNIQUE）
  - **無断キャンセルは、少しずつ**（500件ずつ id を選んで、「今も予約済なら」で更新）。選んだあとに受付された予約は、条件で外れる
  - **会計の金額**: 円の整数。明細に、名前と値段を料金の表から**写して**持つ（料金の表を変えても、過去の会計は変わらない）。合計は確定のときに決めて、列に持つ。下書きのあいだは NULL（CHECK で、状態と合計の有無をそろえる）
  - **明細の入れ直しと確定は、会計の行をロック**（`FOR UPDATE`）してから行う。複数の行（明細）と状態をまたぐので、条件付きの更新1つでは書けないため
  - **決済サービスにはつながない**（2026-11-18 の判断）。支払い済・返金済は、事務スタッフがボタンで記録する。冪等キー・通知（Webhook）・タイムアウトの扱い（K7〜K9）は、決済を足すときに作る。2026-11-19 に、実践の課題（A-1）からも外した。外のサービスが失敗したときの守り方は、メールのサーバーで練習する（課題 D-1）
  - **見える範囲**: 事務スタッフは自院の会計。患者は、自分の、確定した会計だけ（下書きは見せない）。医師には見せない
  - 仮の値（要件 13章の M6）: 受付できるのは開始の30分前から、開始の15分後まで。15分を過ぎた予約済は無断キャンセル
- 弱点・やめる条件: 確定した会計を変えられないことは、アプリのコード（状態の条件）で守っていて、DB では縛っていない。料金の表を画面から変える機能は、まだない（初期データだけ）。無断キャンセルの定期の実行は、通知と一緒にジョブに載せる
- 確かめた数字: 終了を2回押しても会計は1つ。件数が1回の更新の数（2件にして試した）より多い5件でも、全部が無断キャンセルになる。一覧に会計と明細を足しても、行が増えて SQL の本数は変わらない（`spec/graphql/consultation_and_bill_spec.rb`）

## D-013. 通知（outbox と、ジョブの道具）

- 日付: 2026-11-18 ／ 段階: 5 ／ 状態: 決定
- 困ったこと: 予約の応答の中でメールを送ると、メールの都合で予約が遅くなる・失敗する。かといって、コミットのあとに送ると、送る直前に落ちたとき「予約は入ったのに、メールが出ない」になる
- 比べた案:
  - 案A: 予約のトランザクションの中で送る: 単純 ／ ロックを持ったまま外を待つ。巻き戻しても、送ったメールは取り消せない（[database.md](../agents/rules/database.md) で禁止）
  - 案B: コミットのあとに、ジョブを積んで送る: 単純 ／ 積む直前に落ちると、メールが出ない
  - 案C: **outbox**: 「送るメールの記録」を、予約と同じトランザクションで表（`outbox_messages`）に入れ、あとから係が送る: 予約と記録が、必ず両方入るか、両方入らない ／ 表と、送る係が要る。まれに2回送られうる
- 選んだもの: 案C
  - 入れる: `Appointments::Book`・`Cancel` が、同じトランザクションで `Notifications::Outbox.enqueue` を呼ぶ。同じ鍵（`dedup_key` の UNIQUE）の記録は、2件入らない
  - 送る（`Notifications::Dispatch`）: 短いトランザクションで行を取る（`FOR UPDATE SKIP LOCKED` と `locked_until`）→ **トランザクションの外で**送る → 送信済にする。失敗したら残して、5分後にもう一度。5回で、あきらめる（`failed`）
  - 前日のリマインド（`Notifications::EnqueueReminders`）: 明日の予約済に、鍵 `reminder:<予約の id>:<枠の日付>` で入れる。何度動いても、同じ予約の同じ日には1件。時刻を変えて別の日になった予約には、新しい日の前日に、もう一度出る。送る時点で、キャンセルされていたら・別の日になっていたら、送らない（`skipped`）
  - **ジョブの道具は Solid Queue**（要件 13章の M4）。アプリと同じ DB に表を置く。定期の処理（10秒ごとに送る・毎日18時にリマインドを入れる・1分ごとに無断キャンセル）は `config/recurring.yml`。比べたもの: Sidekiq（速い ／ Redis が要る）・Delayed::Job（DB に置く点は同じ ／ 定期の実行は別の道具が要る）
  - 手元では、メールは外へ送らず、受信箱の代わり（Mailpit。http://localhost:58026 ）にたまる
- 弱点・やめる条件: 送ったあと、送信済にする前に落ちると、5分後にもう一度送られる（少なくとも1回。同じメールが2通届きうる）。予約からメールまで、最大で10秒ほど待つ。予約の変更のときのメールは、まだない。`failed` になった記録を見る画面・知らせる仕組みは、まだない。1回の実行（50件）が5分を超えるほどメールのサーバーが遅いと、取った行の期限が切れて、次の実行と2通になりうる。送る係が2つ同時に取るテスト・会計の明細の入れ直しと確定が同時のテストは、まだない（レビューの指摘。2026-11-18）
- 確かめた数字: 記録を入れる所をわざと失敗させると、予約も入らない。送る所を失敗させると、記録は残り、6分後の実行で送られる。2回動かしても、メールは1通。手元で E2E を流すと、予約とキャンセルのメール6通が受信箱に届き、ジョブの失敗は0件（[K10](improvements/K10-mail-not-sent.md)）

## D-014. 事前問診（持ち方・暗号・見える範囲）

- 日付: 2026-11-18 ／ 段階: 8 ／ 状態: 決定
- 困ったこと: 医療機関ごとに違う質問と、その答えを、どう持つか。答えは個人情報の中でも重いので、DB の中身が漏れても読めないようにしたい
- 比べた案:
  - 案A: 質問も答えも普通の表（答えは1質問1行で、答えの列だけ暗号）: 行の形が決まる ／ 表と結合が増える。質問を変えたときの、過去の答えの扱いを決める必要がある
  - 案B: **質問は普通の表、答えは予約ごとに1行で、中身（質問の写しと答えの JSON）をまるごと暗号**: 質問をあとで変えても、過去の問診は答えたときの形のまま読める。暗号にするのが1列で済み、質問の文も漏れない ／ DB の中で、答えを検索・集計できない
- 選んだもの: 案B（`questionnaire_questions`・`questionnaire_responses.payload`）
  - **暗号**: Active Record Encryption（`encrypts :payload`）。鍵は環境変数で渡し、なければ起動しない。手元とテストは `compose.yaml` の捨ててよい鍵、本番は秘密の値
  - **途中まで保存**: `submitted_at` が NULL のあいだは下書き。下書きでは必須を確かめず、提出のときに確かめる。選択肢にない答え・長すぎる文章は、下書きでも断る。一度提出した問診は、「途中まで保存」で直すときも、提出と同じに確かめる（必須を空にして、提出済のまま残さない）
  - **保存は、予約の行をロックしてから**（`FOR UPDATE`）。「診察が始まる前」と確かめたあとに診察が始まって、途中で問診が書き換わる、を防ぐ。ロックを外すと、同時のテストが落ちることを確かめた
  - **入力のエラー**: 悪い所を、質問ごとに、まとめて返す（`field` は `answers.<質問の id>`）。必須や選択肢の決まりは、画面には写さない
  - **見える範囲**（`QuestionnairePolicy`）: 患者は自分の分、医師は自分が担当の分。**事務スタッフには、答えも質問も見せない**（予約は見えるが、問診は null）。答えられるのは、診察が始まる前まで
  - **ログ**: リクエストのログから `answers` を隠す。モデルの `inspect` にも中身を出さない
- 弱点・やめる条件: 答えを条件に探す・集計する必要が出たら、その項目だけ別の列に出す。質問を画面から変える機能は、まだない（初期データだけ）。鍵を替える手順（前の鍵でも読めるようにしておく）は、まだ試していない
- 確かめた数字: DB の列を直接読むと、答えも質問の文も含まれていない。事務スタッフ・ほかの患者・担当でない医師・ほかの医療機関の人には見えないことを、GraphQL を通して確かめた（`spec/services/questionnaires/questionnaire_spec.rb`）

## D-015. 監査ログ（何を・どこで残すか、変えられないようにする方法）

- 日付: 2026-11-18 ／ 段階: 8 ／ 状態: 決定
- 困ったこと: 誰が・いつ・どの患者の・何を見たか、変えたかを、あとから追えるようにする。記録そのものは、変えられない・消せないようにしたい
- 決めたこと:
  - **1つの表に、足すだけ**（`audit_logs`）。した人（種類と id）・操作・どの患者の・何を（種類と id）・いつ。操作の一覧は `AuditLog::ACTIONS` の1か所
  - **変えた、の記録は、業務の処理の中で、同じトランザクションに入れる**（`Audit.record`）。変えたのに記録がない、を起こさない。断られた操作は残さない。比べた案は、モデルのコールバックで自動に残す（付け忘れがない ／ 「誰が」「どの操作として」が、モデルからは分からない）
  - **見た、の記録**は、問診の答えを読んだとき（`QuestionnaireType#answers`）と、会計の明細を読んだとき（`BillType#items`）。入口ではなく項目に置いたので、どの道からたどって読んでも残る。1回のリクエストの分は、まとめて1本の INSERT で入れる（`Sources::AuditView`）。一覧に出る予約・患者の名前・会計の状態と合計は、残していない
  - **システムがしたこと**（無断キャンセルにする定期の処理）も残す。した人の種類を `System`、id を NULL にする（CHECK で、人なら id あり・システムなら id なし、にそろえる）
  - **インデックスは1本だけ**（医療機関・日時・id。新しい順に読むため）。書き込みが多い表なので、インデックスを増やすほど、1行足すたびの書き込みが増える
  - **見られる人**: 自院の分を、管理者の事務スタッフだけ（`staff_members.admin`）
  - **変えられない・消せない**は、モデル（`readonly?`・`before_destroy`）で守る
- 弱点・やめる条件: **DB の側では縛っていない**。SQL を直接流せば、変えられる・消せる。縛るには、更新と削除を断るトリガーか、INSERT しか許さない権限のロールが要る。トリガーは `schema.rb` に書き出されないので、スキーマの持ち方を SQL（`structure.sql`）に変える必要があり、今回は見送った。「見た」の記録は、読むリクエストの中で書き込みが起きる（読むだけの DB には流せない）。一覧を見た、は残らない。保存や確定の結果として答え・明細が返るときにも「見た」が1件残るので、1回の操作で2件になることがある。診療枠を作る・閉じる、ログイン、通知の送信は、患者のデータではないので残していない
- 確かめた数字: 予約 → 問診 → 受付 → 診察 → 会計の確定 → 支払い済 → 返金、で9件が、順番どおりに残る。記録を入れる所をわざと失敗させると、変更も入らない。管理者でない事務スタッフ・医師・患者・ほかの医療機関の管理者には、1件も出ない（`spec/services/audit/audit_log_spec.rb`）

## D-016. ダッシュボードの集計

- 日付: 2026-11-18 ／ 段階: 8 ／ 状態: 決定
- 困ったこと: 日ごと・医師ごとの、予約の件数・キャンセルの割合・売上を出す
- 比べた案:
  - 案A: **開くたびに、その場で集計する**（SQL 1本。期間は31日まで）: 単純で、常に最新 ／ データが増えるほど遅くなる
  - 案B: 集計の表を、定期のジョブで作っておく: 読むのは速い ／ 更新の遅れと、作り直しの仕組みが要る
- 選んだもの: 案A（`Dashboards::DailyQuery`）
  - 予約と枠を結合して、日（日本時間）と医師でまとめる。状態ごとの件数は `COUNT(*) FILTER (WHERE ...)` で、1回の走査で数える
  - 売上は、支払い済の会計の合計（返金済・請求済は入れない）。会計は予約に1つまで（UNIQUE）なので、結合しても予約の行が増えず、件数が狂わない
  - キャンセルの割合と期間の合計は、画面で計算する（行を足すだけ）
- 弱点・やめる条件: まだ、データを増やして測っていない（K11）。遅くなったら、実行計画を見て、集計の表（案B）を足す。売上を「診察の日」でまとめているので、「支払った日」での売上は出せない
- 確かめた数字: 日と医師が増えても、SQL は2本（集計と、医師の名前のまとめ読み）。日の区切りが日本時間であること、ほかの医療機関の予約と売上が入らないことを確かめた（`spec/queries/dashboard_spec.rb`）

## D-017. 入口と画面を、利用者（患者・事務スタッフ・医師）ごとに分ける

- 日付: 2026-11-18 ／ 段階: 8 ／ 状態: 決定
- 困ったこと: 1つの GraphQL のスキーマと1つの画面に、3種類の利用者の操作が全部載っていた。患者の画面からも、会計の確定や監査ログの操作がスキーマ上は見え（呼べば認可で断られる）、画面も役割で出し分ける分岐が増えていた。使う場面も違う（患者はスマホで予約と受付、事務スタッフは表で一覧と会計、医師はその日の予定）
- 比べた案（バックエンド）:
  - 案A: **入口（スキーマ）を3つ・業務の処理と認可は共有**: その人が使う操作だけが、その人のスキーマに載る。二重予約などの決まりは1か所のまま ／ 型（`Appointment` など）は共有なので、`canStartConsultation` のような項目は、患者のスキーマにも載る
  - 案B: 型も利用者ごとに分ける: 患者のスキーマに、医師用の項目が一切載らない ／ 型のコードが3倍近くになる
  - 案C: フォルダごと（業務の処理・認可まで）3つに分ける: 決まりが複数の場所に書かれ、ずれる
- 選んだもの（バックエンド）: 案A
  - `POST /graphql/patient`・`/graphql/clerk`・`/graphql/doctor`。スキーマは `PatientApi::Schema` などで、共通の設定は `BaseSchema`
  - **ログインは入口ごと**: その入口の利用者の中からだけ探す（患者の入口に医師のメールアドレスを入れても、いないのと同じ）。セッションの合言葉も入口ごとに持つ（3つの画面は同じホストでポートだけが違い、Cookie はポートを区別しないので、1つの Cookie の中で入口ごとのキーに分けた）。同じブラウザで、3つに同時にログインしていられる
  - 落とし穴: `use GraphQL::Dataloader` は、継いだスキーマに引き継がれない。入れ忘れると、まとめ読みが全部エラーになった（`BaseSchema.inherited` で、継ぐたびに入れる）
- 比べた案（フロントエンド）: 3つのアプリ ／ 2つ（患者と、スタッフ）
- 選んだもの（フロントエンド）: 3つのアプリ（`apps/patient`・`apps/clerk`・`apps/doctor`。ポートは 3000・3010・3020）
  - それぞれ、自分用のスキーマから型を作る。患者のアプリから、会計の確定の mutation は、型の上でも書けない
  - 共有: `packages/ui`（見た目）と `packages/web-kit`（Apollo の設定・ログインのフォーム・日付・状態の呼び方・スタッフ共通の部品）
  - **見た目**（医療機関の画面で一般的な作りを取り入れた。特定の製品の画面は写していない）: 落ち着いた青緑を主な色にし、赤は「取り消す・危ない」だけに使う。時刻と金額は桁のそろう数字。状態は、色だけでなく必ず言葉でも出す。予約・キャンセル・会計の確定・診察の終了など、押し間違えると困る操作は、確認の窓を出してから送る。患者の画面はスマホの幅で1列のカード、スタッフの画面は左のメニューと表
- 弱点・やめる条件: ログインのときに作り直すのは、その入口の合言葉だけ（前は Cookie のセッション全体を作り直していた）。ほかの入口のキーは残るので、Cookie を仕込める人が、別の入口の合言葉を残せる（ログインに使う合言葉は毎回作り直すので、影響は小さい）。医師の予定の30秒ごとの取り直しは、取り直しが最初のページだけを取るため、「続きを読み込む」を押したあとは止まる（1日50件を超える医師だけ。そのあいだは、受付済になっても自分で開き直すまで変わらない）。通信が切れているとき・画面が隠れているときは取り直さず、同じ文の失敗の知らせは重ねて出さない（2026-11-18 に直した。前は、知らせが30秒ごとに積み上がり、足したページも消えていた）。3つのアプリで同じような画面（予約の一覧など）を、それぞれ持つ。共通にしたくなったら、まず `packages/web-kit` に「データを取らない部品」として下ろす。医師の予定は、受付済になったことに気づくために30秒ごとに取り直している（リアルタイムの知らせは、課題 D-4）
- 確かめた数字: どの入口に、どの操作が載っているかを、テストで固定した（`spec/graphql/schema_spec.rb`）。3つの入口で、ほかの種類の人がログインできないこと・1つをログアウトしても、ほかは切れないことを確かめた（`spec/requests/graphql_spec.rb`）。E2E 9本が、3つの画面をまたいで通る。レビュー（2026-11-18）で、確認の窓が送信中にも閉じられて、2つ目の予約を並んで送れる穴が見つかった。送信中は窓を閉じさせず、時刻のボタンも止める形に直し、部品のテストで確かめた

## D-018. E2E を CI に入れ、main をブランチの保護で守る

- 日付: 2026-11-19 ／ 課題: F-1 ／ 状態: 決定
- 困ったこと: E2E（Playwright 9本）は手元でしか走らず、走らせ忘れると、3つの画面をまたぐ流れが壊れても気づけない。手元では日本時間の23:25以降に1本が飛ばされる。CI は通らなくてもマージできた
- 比べた案（E2E の API の起動）:
  - 案A: **Rails をそのまま起動する**（`ruby/setup-ruby` の gem のキャッシュ＋PostgreSQL の service）: 速い ／ 手元（Docker）と起動の仕方が違う
  - 案B: 手元と同じ `docker compose up`: 手元と同じ ／ 毎回イメージを作り、gem を入れ直すので遅い
- 選んだもの: 案A。手元との違いは、起動の仕方だけ（同じ版の Ruby・PostgreSQL・同じ初期データ）
  - 環境は development（初期データが、開発の環境でだけ入るため）。ジョブの係（Solid Queue）は動かさない。E2E は、メールが届いたかを見ないため
  - Playwright のブラウザは、版ごとにキャッシュする
  - 画面は、先に組み立ててから本番の形（`next build` → `next start`）で起動する。開発用のサーバー（`next dev`）だと、ページを初めて開いたときの組み立てで、たまに5秒の待ちを超えて落ちた（PR #3 の初回）
  - 落ちたときは、Playwright の記録（trace）と Rails のログを、7日だけ残す
- ブランチの保護（main）: 3つのジョブ（API・画面・E2E）が通らないとマージできない。直接の push と、履歴の書き換え（force push）を断る。管理者は守りを外せる（1人の練習なので、詰まったときの逃げ道を残す）。`template` は保護しない（main に合わせて動かすため）
- 弱点・やめる条件: E2E が CI の中でいちばん遅い（2分ほど）。PR のたびに走らせて待つのがつらくなったら、F-5 で測ってから、走らせる条件を絞る
- 確かめた数字: 初回の CI で、E2E のジョブが 2分3秒（そのうち E2E が 63秒・ブラウザを入れるのが 20秒）。9本すべてが通った
