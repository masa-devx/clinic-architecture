# 実践の課題（template ブランチから切って進める）

`template` ブランチは、「ひととおり動く、きちんと作った土台」。ここから課題ごとにブランチを切って、バックエンドの仕事でよく求められること（下の6つ）を、手を動かして練習する。

Rails のバックエンドの仕事の例と、ここでの練習の対応:

| 求められる仕事 | ここでの練習 | 課題 |
| --- | --- | --- |
| Rails / GraphQL での新機能の設計・開発 | 要件から、表・スキーマ・処理・テストを自分で設計して足す | A |
| 既存機能の改善・リファクタリング、技術的負債の解消 | 動きを変えずに直す。直す前に、テストで今の動きを固める | B |
| 不具合の調査・パフォーマンス改善（Sentry など） | 仕込まれた不具合・遅さを、ログと実行計画から見つけて直す | C |
| 非同期処理（Sidekiq など）の設計・運用 | ジョブの失敗・再試行・重複・詰まりを起こして、守り方を決める | D |
| RDB の設計・運用、クエリとインデックスの最適化 | 100万件を入れて、実行計画を読み、インデックスを決める | E |
| アーキテクチャ・開発プロセス・CI/CD の改善 | GitHub に置いて CI を通す。運用の道具を入れる。本番の形に置く | F |

**主な目的は、Ruby on Rails と、それに付随するバックエンドの知識（DB・SQL・トランザクション・非同期処理・調査の道具）を理解すること**。画面だけの課題（C-3 など）は、後ろへ回す。道具は、無料で使えるものだけを使い、入れる前に「なぜ要るか」を決める（[pm](../agents/skills/pm/SKILL.md) の5つの問い）。

### よくある構成との違い

Rails のバックエンドでよく使われる構成と、ここの構成は、いくつか違う。違いそのものが、課題になる。

| 部分 | よくある構成 | ここ | 練習で埋めるなら |
| --- | --- | --- | --- |
| DB | MySQL（Aurora） | PostgreSQL | E-4（MySQL でできないこと・代わりの書き方を調べる） |
| ジョブ | Sidekiq（Redis） | Solid Queue（DB） | D-3（Sidekiq に載せ替えて、違いを確かめる） |
| 監視 | Sentry・Datadog・CloudWatch | なし（1行の JSON のログだけ） | C-1 |
| インフラ | ECS Fargate・ALB・Terraform | 手元の Docker だけ | F-4 |

## 2. 進め方（1つの課題 = 1つのブランチ）

1. `git switch template && git switch -c practice/<記号>-<名前>` で切る
2. **先に、自分で考える**: 何が問題か・どう調べるか・どう直すかを、`docs/steps/` に短く書く（[explain-step](../agents/skills/explain-step/SKILL.md) の6つの問い）
3. 調べる・直す。AI に書かせてもよいが、説明できない所を残さない
4. 記録する: 判断は [decisions.md](decisions.md)、課題と数字は [improvements/](improvements/README.md)
5. PR を作って、自分でレビューの観点を書く（F-1 のあと）

C の課題（不具合の調査）は、**AI に「不具合を仕込んだブランチ」を作らせて、何を仕込んだかは教えてもらわずに調べる**。「原因が分からない所から始める」調査に近づける。

### E. DB の設計とクエリ

| # | 課題 | やること | 残すもの |
| --- | --- | --- | --- |
| E-1 | **100万件を入れて、一覧の実行計画を読む**（K3・K4） | 予約を100万件入れるコマンドを作る。予約の一覧・空いている枠・ダッシュボードの `EXPLAIN (ANALYZE, BUFFERS)` を読み、今のインデックスが効いているか確かめる。効いていなければ、列の順番を決め直す | 読んだ行・時間（前 → 後） |
| E-2 | OFFSET とカーソルを比べる | わざと OFFSET の一覧を作り、深いページの時間と、途中で行が増えたときの重複を、カーソルと比べる | 深いページの時間 |
| E-3 | 大きな表の定義を、止めずに変える（K13） | 100万件の表に、列を足す・名前を変える・NOT NULL を付ける。その間に画面を動かして、止まる時間を測る。手順（足す → 両方に書く → 切り替える → 消す）で直す | 止まった時間（前 → 後） |
| E-4 | MySQL なら、どう書くか | 部分 UNIQUE・排他制約・`SKIP LOCKED`・`FILTER`・timestamptz が、MySQL でどうなるかを調べ、代わりの設計を書く（実装は、二重予約の1つだけでよい） | 対応の表 |
| E-5 | ダッシュボードを、集計の表にする（K11） | E-1 のデータで遅さを測ってから、集計の表と、作り直しのジョブを足す | 時間（前 → 後）・更新の遅れ |

### D. 非同期処理

| # | 課題 | やること | 残すもの |
| --- | --- | --- | --- |
